# Agent Pages REST API

The REST API lets an owner create, inspect, update, export and delete static sites. Its base is the application origin, for example `https://app.example.com/api`. Published content is served from the separate URL returned as `site.url`.

## Authentication and request rules

Create an owner API key in the dashboard and send it on every request:

```http
Authorization: Bearer agp_...
```

Store the key in an environment variable or secret manager. Do not put it in prompts, source files, URLs or logs. Browser session cookies are not accepted by this API. Non-browser clients should omit `Origin`; when present it must exactly match the configured application origin.

JSON requests require `Content-Type: application/json`. Request bodies and list pages are bounded by the installation's configured limits. Site IDs and revision IDs are 32 lowercase hexadecimal characters. An `operationId` is a UUID generated by the caller. The UUIDs in this guide are placeholders: generate a fresh one for each new command, then retain it only to retry that exact command.

The API is currently unversioned under `/api`. Clients should use the documented routes and ignore additional response fields.

## Routes

| Method | Route | Input | Result |
| --- | --- | --- | --- |
| `POST` | `/api/sites` | Create body | `201` create receipt |
| `GET` | `/api/sites?limit=&cursor=` | `limit` 1–50; opaque cursor | Site page |
| `GET` | `/api/sites/:siteId` | None | Site metadata |
| `GET` | `/api/sites/:siteId/revisions` | None | Retained revision history |
| `GET` | `/api/sites/:siteId/files?revisionId=&limit=&cursor=` | `limit` 1–100; optional pinned revision | File page |
| `GET` | `/api/sites/:siteId/file?path=&revisionId=` | Required path; optional pinned revision | Raw file bytes |
| `PUT` | `/api/sites/:siteId/files` | JSON write body or multipart body | File-mutation receipt |
| `POST` | `/api/sites/:siteId/files/delete` | Delete-files body | File-mutation receipt |
| `POST` | `/api/sites/:siteId/restore` | Restore body | Site-mutation receipt |
| `PUT` | `/api/sites/:siteId/visibility` | Visibility body | Site-mutation receipt |
| `PUT` | `/api/sites/:siteId/expiration` | Expiration body | Site-mutation receipt |
| `GET` | `/api/sites/:siteId/export` | None | ZIP of the current revision |
| `DELETE` | `/api/sites/:siteId` | Delete body | Delete receipt |

Mutation routes reject query parameters. Duplicate query keys and caller-supplied identity fields are rejected. Cursors are opaque and scoped to the owner and resource; send them back unchanged. When paging files, keep using the response's `revisionId` so every page comes from one immutable revision.

## Site and receipt objects

A site has this shape:

```json
{
  "id": "0123456789abcdef0123456789abcdef",
  "name": "Product preview",
  "visibility": "private",
  "version": 1,
  "revisionId": "fedcba9876543210fedcba9876543210",
  "url": "https://0123456789abcdef0123456789abcdef.sites.example.com",
  "openUrl": "https://app.example.com/sites/0123456789abcdef0123456789abcdef/open",
  "createdAt": "2026-09-17T10:00:00.000Z",
  "updatedAt": "2026-09-17T10:00:00.000Z",
  "expiresAt": null,
  "sizeBytes": 41,
  "fileCount": 1
}
```

Every successful mutation includes the caller's `operationId` and `operationExpiresAt`, the deadline for exact replay. Create and site-mutation receipts contain `site`. File-mutation receipts also contain sorted `changedPaths` and `deletedPaths`. A delete receipt contains `siteId`, the final `version`, `deleted: true` and `cleanupPending`.

Creation starts at version 1. A mutation that changes state advances the site version by one. A no-op returns a receipt without advancing it. `GET /api/sites/:siteId` returns the version at the root as `version`; mutation receipts return it as `site.version`. Updating files preserves the site ID, URL, visibility and expiration.

## Revision history and restoration

`GET /api/sites/:siteId/revisions` returns the active revision first, then retained previous revisions ordered by descending `lastActivatedVersion`:

```json
{
  "site": { "id": "0123456789abcdef0123456789abcdef", "version": 3, "revisionId": "fedcba9876543210fedcba9876543210" },
  "historyLimit": 5,
  "revisions": [
    { "revisionId": "fedcba9876543210fedcba9876543210", "active": true, "publishedVersion": 1, "lastActivatedVersion": 3, "createdAt": "2026-09-17T10:00:00.000Z", "lastActivatedAt": "2026-09-19T10:00:00.000Z", "sizeBytes": 41, "fileCount": 1 }
  ]
}
```

The `site` object has the complete site shape shown above; it is shortened here. `historyLimit` counts previous revisions beyond the active revision. The operator can set it from 0 through 50; the default is 5. `publishedVersion` records the revision's first publication and `lastActivatedVersion` its latest activation. Either version field may be `null` for a revision migrated from older storage. `createdAt` and `lastActivatedAt` are timestamps. History is owner-only even for a public site.

Restore one of the listed revisions with `POST /api/sites/:siteId/restore`:

```json
{"operationId":"88888888-8888-4888-8888-888888888888","expectedVersion":3,"revisionId":"fedcba9876543210fedcba9876543210"}
```

The result is a site-mutation receipt. Restoring a previous revision reactivates its immutable files and increments the site version by one; it keeps the site ID, URL, visibility and expiration. Restoring the active revision checks `expectedVersion` and returns a no-op receipt without incrementing it. Only retained revisions are restorable; a retired revision returns `REVISION_UNAVAILABLE`. Before activation the server verifies the revision's file metadata and digests against disk. The same operations are available as MCP `list_site_revisions` and `restore_site_revision`.

## Create a private site

New sites are always private. The trimmed site name must contain 1–100 characters, and the root `index.html` is required. `expiresInSeconds` may be 60 through 2,592,000, or `null` for no expiration. Omit it to use the owner's default.

```sh
curl --fail-with-body https://app.example.com/api/sites \
  -H "Authorization: Bearer $AGENT_PAGES_API_KEY" \
  -H 'Content-Type: application/json' \
  --data '{
    "operationId": "11111111-1111-4111-8111-111111111111",
    "name": "Product preview",
    "files": [
      {"path": "index.html", "content": "<!doctype html><h1>Preview</h1>"},
      {"path": "styles/site.css", "content": "body { max-width: 60rem; }"}
    ]
  }'
```

The response is a create receipt:

```json
{
  "site": {
    "id": "0123456789abcdef0123456789abcdef",
    "name": "Product preview",
    "visibility": "private",
    "version": 1,
    "revisionId": "fedcba9876543210fedcba9876543210",
    "url": "https://0123456789abcdef0123456789abcdef.sites.example.com",
    "openUrl": "https://app.example.com/sites/0123456789abcdef0123456789abcdef/open",
    "createdAt": "2026-09-17T10:00:00.000Z",
    "updatedAt": "2026-09-17T10:00:00.000Z",
    "expiresAt": null,
    "sizeBytes": 57,
    "fileCount": 2
  },
  "operationId": "11111111-1111-4111-8111-111111111111",
  "operationExpiresAt": "2026-09-18T10:00:00.000Z"
}
```

## Read metadata and files

List responses use `{ "sites": [...], "cursor": null }` and `{ "revisionId": "...", "files": [...], "cursor": null }`. Each file entry contains `path`, `sizeBytes`, server-assigned `contentType` and a SHA-256 `digest`. A pinned revision read works while that revision remains retained or leased and its files remain on disk; a cursor does not keep it available indefinitely.

```sh
curl --fail-with-body \
  -H "Authorization: Bearer $AGENT_PAGES_API_KEY" \
  'https://app.example.com/api/sites/0123456789abcdef0123456789abcdef/files?limit=100'

curl --fail-with-body \
  -H "Authorization: Bearer $AGENT_PAGES_API_KEY" \
  'https://app.example.com/api/sites/0123456789abcdef0123456789abcdef/file?path=styles%2Fsite.css&revisionId=fedcba9876543210fedcba9876543210'
```

Raw file responses include `Content-Type`, `Content-Length`, `X-Agent-Pages-Revision` and `X-Agent-Pages-Digest`. Export responses are `application/zip` and include `X-Agent-Pages-Revision`.

## JSON writes

Use JSON for UTF-8 text. Replace or add several paths atomically with one request:

```json
{
  "operationId": "22222222-2222-4222-8222-222222222222",
  "expectedVersion": 1,
  "files": [
    {"path": "index.html", "content": "<!doctype html><h1>Updated</h1>"},
    {"path": "notes.md", "content": "# Release notes\n"}
  ]
}
```

Send that body with `PUT /api/sites/:siteId/files`. Delete files with:

```json
{
  "operationId": "33333333-3333-4333-8333-333333333333",
  "expectedVersion": 2,
  "paths": ["old.css", "images/old.png"]
}
```

Send the delete body to `POST /api/sites/:siteId/files/delete`. Every revision must retain `index.html`.

## Binary and multipart writes

Use multipart for binary data and large batches. The first part must be one text field named `manifest`. It maps canonical site paths to unique multipart field names:

```json
{
  "operationId": "44444444-4444-4444-8444-444444444444",
  "expectedVersion": 2,
  "files": [
    {"path": "index.html", "partName": "page"},
    {"path": "images/hero.png", "partName": "hero"},
    {"path": "guide.pdf", "partName": "guide"}
  ]
}
```

Every referenced file part must follow the manifest exactly once and in the same order. Extra fields, duplicate names, missing files, reordered files, interrupted framing or limit violations reject the whole publication; the previous revision stays active. Client filenames and part MIME types are ignored. Agent Pages assigns content types from the destination paths.

```sh
curl --fail-with-body \
  -X PUT "https://app.example.com/api/sites/$SITE_ID/files" \
  -H "Authorization: Bearer $AGENT_PAGES_API_KEY" \
  -F 'manifest={"operationId":"44444444-4444-4444-8444-444444444444","expectedVersion":2,"files":[{"path":"index.html","partName":"page"},{"path":"images/hero.png","partName":"hero"},{"path":"guide.pdf","partName":"guide"}]}' \
  -F 'page=@dist/index.html' \
  -F 'hero=@dist/images/hero.png' \
  -F 'guide=@dist/guide.pdf'
```

The default size limits are 100 files per batch, 20 MiB per file and 25 MiB per multipart body; operators may change them. The API has a fixed 30-second multipart receive deadline.

## Visibility, expiration and deletion

These bodies all require the current site version and a fresh operation ID:

```json
{"operationId":"55555555-5555-4555-8555-555555555555","expectedVersion":3,"visibility":"public"}
```

```json
{"operationId":"66666666-6666-4666-8666-666666666666","expectedVersion":4,"expiresInSeconds":86400}
```

Send them to the visibility and expiration routes respectively. Use `"visibility": "private"` to revoke subsequent anonymous access. Use `"expiresInSeconds": null` to remove expiration from a live site. Expiration is terminal: the public content hostname returns 404, and authenticated content reads and ordinary mutations return `SITE_EXPIRED`. Owner metadata remains available until reclamation, and the owner may still delete the expired site.

Delete a whole site with `DELETE /api/sites/:siteId` and this body:

```json
{"operationId":"77777777-7777-4777-8777-777777777777","expectedVersion":5}
```

## Concurrency and idempotency

Read `site.version` immediately before an existing-site mutation and send it as `expectedVersion`. On `VERSION_CONFLICT`, fetch current metadata, reconcile the intended change, and issue a new command with a new operation ID.

Mutation receipts are retained for at least 24 hours. If a response is lost, retry the exact method, route and body with the same operation ID. The server returns the original result without applying the mutation twice. Reusing an operation ID for different input or a different operation returns `IDEMPOTENCY_CONFLICT`. After `operationExpiresAt`, inspect current state before deciding whether another mutation is needed.

## Paths and supported files

Paths are relative canonical POSIX paths up to 512 UTF-8 bytes and 32 segments. They cannot start with `/`, contain backslashes or literal percent signs, use empty, `.`/`..` or hidden segments, or begin with the reserved `_agent` segment. A file and directory cannot occupy the same path.

Supported extensions are HTML, CSS, JavaScript, JSON, PNG, JPEG, WebP, AVIF, GIF, SVG, ICO, WOFF/WOFF2, TXT, XML, web manifests, source maps, Markdown and PDF. The server validates the complete tree and requires root `index.html`.

## Errors

Errors are JSON and include a correlation ID:

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "Site version does not match",
    "retryable": false,
    "requestId": "9a3a3666-55a2-4da8-926b-4f75cf312239",
    "details": {"currentVersion": 4}
  }
}
```

| Status | Codes |
| --- | --- |
| `400` | `INVALID_INPUT`, `INVALID_PATH` |
| `401` | `UNAUTHENTICATED` |
| `404` | `NOT_FOUND` |
| `409` | `VERSION_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `REVISION_UNAVAILABLE`, `QUOTA_EXCEEDED` |
| `410` | `SITE_EXPIRED` |
| `413` | `PAYLOAD_TOO_LARGE` |
| `415` | `UNSUPPORTED_MEDIA_TYPE` |
| `429` | `RATE_LIMITED` |
| `503` | `BUSY`, `STORAGE_UNAVAILABLE` |

`BUSY`, `RATE_LIMITED` and `STORAGE_UNAVAILABLE` have `retryable: true` and include `Retry-After: 60`. Use bounded retries and preserve the original operation ID. Other failures require changing the request or reconciling state.
